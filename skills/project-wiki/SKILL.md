# Project Wiki

交付一套可信、可定位、可持续维护的项目知识。仓库中的 Markdown 阅读是完整可用的交付形态；没有 Web server 的 Go/Rust/CLI 项目同样适用，不为 Wiki 增加服务器或运行时。

## 先确定范围

阅读项目已有协作规范、README、文档入口、构建/运行配置及与任务相关的实现、测试。确认工作区已有改动。优先采用既有 Wiki、目录、包管理器和技术栈，不将建立 Wiki 扩展成业务目录重构。

按请求选择模式，不要求每次执行全部模式：

- **建立**：从当前机制提取有持续价值的知识，建立最小主题结构和阅读入口。
- **整理**：核验现有材料，优先更新或合并原主题；删除失效与重复内容，保留需要兼容的历史引用。
- **维护**：定位本次变化影响的既有事实；必要时更新相关主题，局部实现/外观变化可以无需改 Wiki。

若用户没有要求网页，也没有必须保留的既有网页，就采用仓库阅读。网页启用、公开范围或权限变动影响架构/授权时，遵循目标项目的讨论边界；现有授权不重复确认。在线编辑/上传/发布后台是额外范围，不把“网页浏览”解释成 CMS 编辑系统。

## 知识与组织

内容工作阅读 [知识准入与同步](references/knowledge-policy.md)；建立、合并或重排主题时再阅读 [内容组织](references/content-organization.md)。

- 以当前实现、配置和明确工程约束为事实依据，交叉核对相关测试。不能由缺失功能推断产品定位，不能由代码存在推断线上验收成功。
- 记录影响理解、修改或运行的语义、关系、条件与失败恢复；不逐文件翻译代码，不为局部 UI、每次测试或任务施工留痕。
- README 负责介绍/运行/导航，助手规范负责贡献方式与约束，Wiki 负责当前业务与工程知识，Git 保留过程。保留项目已有助手规范文件名，不强制新增另一套工具专用文件。
- 主题根据真实内容生长，默认可选 `content/wiki/`；已有合理路径则沿用。不凑栏目，不按源码文件逐页拆分，不强制 Next.js 式目录。
- 已有事实受影响必须修正；新内容按准入标准筛选，优先落入原主题。不要机械要求每次改代码都改 Wiki。
- 发现疑似代码缺陷单独反馈，不能通过文档整理改变业务规则。事实暂不可确认时不写成既定机制，具体阻碍在交付说明中说明。

## 可选扩展

只读取与任务相关的参考，默认不安装依赖：

- 校验：阅读 [校验契约](references/validation.md)。按现有工具链选择校验方式；没有合适运行时就进行有边界的人工核验，或在用户要求自动化时提供适配方案，不为了 Go 工具引入 Node。
- 网页浏览：阅读 [框架无关的网页接入](references/web-browsing.md)。Express 等沿用现有路由、模板和认证，按共享内容/链接契约接入，不迁移框架。
- Next.js：在已启用网页且采用 App Router 时，阅读 [Next.js 接入](references/nextjs-integration.md)。`assets/nextjs-wiki/` 提供可改造的读取、AST 校验、别名、渲染和路由示例，先核对目标项目的当前版本文档及依赖，不直接覆盖项目文件。
- 图表：关系、状态或流程确实更易通过图理解时，阅读 [图表扩展](references/diagrams.md)。无需图表时不引入 Mermaid、浏览器或图表生成命令。

Next.js 资产是参考，不是自动安装器；核心规则不依赖这些资产、Node、React、shadcn 或任何特定角色模型。仓库阅读或其他框架不得默认复制它们。

## 交付与验收

按 [校验契约](references/validation.md) 核对真实入口、当前事实、引用和删除材料的知识去向。网页另验证直达/刷新、导航、鉴权、内容打包与实际渲染；沿用项目测试策略，不强制 UI 自动化。

维护任务只验证受影响范围。需要测试时验证实质边界，例如根目录逃逸、越权读取、别名冲突与无效锚点；不要只匹配生成文案或目录数量。说明实际运行的检查及其局限，不把历史结果、未执行的镜像构建或真实联调当作本次通过。

完成后交付知识入口、关键组织选择与验证结果。临时方案及专项入口在工作结束后清理，知识已迁入长期主题后由 Git 保留过程。提交、推送、公开和部署遵循当前用户授权与仓库约定，本技能不另设一套默认 Git/发布规则。
